# 项目介绍话术（面试 / 评审用）

适用场景：面试自我介绍、项目评审答辩、现场演示讲解。
文中出现的规则名、阶段名、工具数量、用例数量均与仓库实际实现一致，可直接引用。

参考事实基线：

- 判定规则：R-01 事实边界、R-02 推断处理、R-03 缺失信息、R-04 证据要求、R-05 矛盾处理、R-06 下一步行动；
- 阶段定义：S5 赢单/签约、S4 决策审批、S3 商务评估、S2 方案验证、S1 需求初探、S0 线索；
- 工具链 10 个确定性工具，接口 6 个，自测用例 29 个（实测 0.66s 跑完）；
- 零第三方依赖，断网可跑；`plan` / `trace` / `context` 随响应返回。

## 一、一句话定位（30 秒电梯版）

这是一个把销售拜访记录自动变成**可复核 CRM 商机**的 Agent：输入一段中文拜访纪要，
输出 CRM 十字段结构化字段、S0–S5 阶段判定、R-01~R-06 规则校验报告和结构化追问。

它最大的特点不是「用大模型做抽取」，而是**判定权不收在模型手里**——
大模型只决定调用顺序，字段值、状态、证据、阶段、合规结论全部来自外置规则的确定性引擎，
所以每条结论都能回指到规则原文和客户原话。

## 二、两分钟版：问题 → 取舍 → 证据 → 边界

### 2.1 先说业务问题

销售拜访记录是自由文本，录入 CRM 靠人肉整理，不同人写出不同版本。
直接让大模型抽取的典型失败是「看起来对，但没法复核」：金额多个零、把「可能」写成「确定」、
客户没提预算却补了一个数。

所以真正的核心问题不是「抽得准不准」，而是**结论能不能被复核、错了能不能追溯**。

### 2.2 再说关键取舍

把判定权归属做成架构的第一原则：规则引擎是工具集（10 个确定性工具，每个带
`requires` / `produces` 契约），模型是规划器加文案润色器，**没有任何写权限**——
不能产出字段值、状态、证据、阶段或合规结论。

### 2.3 然后是四个具体机制

- **字段三态**（事实 / 推断 / 未确认）加原话证据，未确认时 `value` 为 `null`，宁缺勿编；
- **矛盾双保留**不选边，按 R-05 标风险并生成追问（且做了口径区分，「总预算 80 万」
  与「项目投入 45 万」不会被误判成矛盾）；
- **阶段自 S5 向 S0 扫描**，计划性口径会被拦截——「合同正在走流程」判不了 S5，
  判不了就明确说明缺什么证据；
- **失败降级链**：模型不可用走默认编排，单工具异常隔离后兜底补齐，文件解析失败给可操作建议。

### 2.4 最后给证据

29 个用例 0.66 秒跑完，覆盖硬规则正反例、模型打桩四分支、解析降级和接口冒烟；
零第三方依赖，断网可跑；`plan` / `trace` / `context` 随响应返回，
页面上能直接看到每一步工具调用、理由和耗时。

### 2.5 边界要主动说

OCR、多商机自动拆分、持久化审计、鉴权限流明确不做，属于生产化批次。

## 三、五分钟深讲：一个核心矛盾 + 四个设计响应

围绕一句话展开：**模型负责怎么说，代码负责说对**。

### 3.1 自主规划

两层规划。有模型时由模型从工具清单里选顺序，模型给的计划要过四道校验：白名单、依赖补齐、
必需项兜底、步数上限；没模型时走规则引擎默认编排。两条路径的判定结果完全一致，
`plan.source` 会明确标注本次来自「模型规划」还是「规则引擎默认编排」。

### 3.2 工具契约化

每个工具声明 `parameters` / `requires` / `produces` / `optional`，
新增能力等于新增契约，编排器零改动——本项目从 8 个工具扩到 10 个就是零改动完成的。
工具必须确定性、幂等，拿不到前置产物时返回 `skipped` 而不是抛异常。

### 3.3 双轨上下文

规则引擎永远使用完整原文（保证召回与证据完整），只有送给模型的上下文压缩：
原文超 2000 字取头 1500 + 尾 500，追问答案截断到 200 字，字段值截断到 80 字，总预算 6000 字符。
压缩统计（原文长度、模型上下文字符数、省略字数、证据条数）随响应回传，
让「压缩有没有失真」可观测。

### 3.4 可观测性

把 `plan` / `trace` / `context` 当一等输出：`plan` 说明本次编排来源与理由、
被拒绝的非法工具；`trace` 逐步记录工具名、编排理由、状态、耗时、产物摘要。
排障、评审、演示复用同一份数据，界面上有「执行轨迹」面板可视化。

## 四、现场演示脚本（3 分钟）

| 步骤 | 动作 | 要说明的点 |
| --- | --- | --- |
| 1 | 打开页面，指顶部状态 | 判定引擎是规则引擎，模型可选；全程不用网络 |
| 2 | 点样例 1 规范完整 | S4 决策审批、十字段齐全、校验「合规 0 项问题」 |
| 3 | 点样例 2 关键信息缺失 | 预算/决策人 `value` 为 `null`，未确认信息写明「按 R-03 不补全」 |
| 4 | 在追问里填「预算 30 万已批」「张总最终签字」并重新分析 | **最亮的一段**：字段升级为事实、阶段 S1→S3、高亮变化字段 |
| 5 | 点样例 3 矛盾 | 三处矛盾双版本保留 + R-05 高风险项 |
| 6 | 点样例 4 模糊措辞 | 「可能」「挺感兴趣」降级为推断，S1 被拦并说明原因 |
| 7 | 展开「规则依据」和「执行轨迹」 | 规则外置可审，10 步工具调用有理由有耗时 |

第 4 步是全场重点，它证明的不是「能抽取」，而是**追问闭环真的驱动了判定变化**。

## 五、高频追问应答库

| 追问 | 应答要点 |
| --- | --- |
| 为什么不让大模型直接判定？ | 题目明确不允许只依赖模型常识；业务上判定要能回指规则原文；工程上要可复现——关掉模型，同一输入输出逐字段一致 |
| 正则加词典召回够吗？ | 这是最诚实的边界：强在确定性与可审计，弱在口语化长句和新词。改进路径是向量召回做候选生成、规则做最终判定，词典缺口从失败样例自动挖掘 |
| 怎么证明效果？ | 当前是断言式测试，覆盖四类失败形态和硬规则正反例；缺口是统计式评估——没有 golden set 和字段级 P/R 指标，这是已知的第一个 P0，放在第 1 批迭代 |
| 模型输出会不会污染结果？ | 模型不能写任何判定产物；唯一写权限是润色已确认字段的文案，而这也正是目前唯一薄弱面（还没做 diff 校验），已列进改进清单 |
| 模型挂了怎么办？ | 单次失败回退默认编排；连续 2 次失败熔断 60 秒；全程零模型时输出完全确定 |
| 长文本怎么处理？ | 双轨上下文：规则引擎用完整原文，只有模型上下文压缩，并把省略字数与上下文长度回传 |
| 怎么处理矛盾？ | R-05 双保留 + 标风险/待确认 + 生成追问，不替客户选边；口径差异不误报 |
| 为什么坚持零依赖？ | 演示环境的确定性优先：断网、没装包、双击脚本就能跑。代价是 UI 只能用原生，这是取舍不是限制 |
| 如果重做会改什么？ | golden set 前置、输出契约先冻结、`extract.py` 拆 extractor 插件、证据 span 化、润色加 diff 校验 |

## 六、三个要避开的讲法

1. 别用「大模型驱动」当卖点，这个项目的立身之本恰恰相反；
2. 别一上来讲技术栈，先讲业务问题和取舍；
3. 别只演示样例 1，样例 2、3、4 才是设计能力的体现。
