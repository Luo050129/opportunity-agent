# 本次开发的关键决策与踩坑记录

记录**真实发生过**的问题与当时的选择，附通用教训，方便下次少走弯路。

## 一、关键设计决策（ADR 速览）

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 判定主体 | 规则引擎（词典 + 正则 + 位置规则），模型只规划与润色 | 题目要求"不允许只依赖大模型常识自由判断"，结论要能回溯到规则原文 | 口语化长句召回有限，需持续维护词典 |
| 交付形态 | 本地网页 + 零第三方依赖 | 现场断网、环境没装包也能跑 | UI 只能用原生 HTML/CSS/JS |
| 会话状态 | 服务端无状态，前端回传完整上下文 | 免持久化、可多窗口并行、重启不丢 | 请求体更大，需要上下文压缩配合 |
| 事实判定 | 三态（事实/推断/未确认）+ 原话证据 | "宁缺勿编"比"看起来完整"更重要 | 输出更长，需要更好的可视化 |
| 矛盾处理 | 双方原话同时保留 + 标待确认，不选边 | 规则 R-05 明确要求，替客户选边风险高 | 阶段判定会带 conflict 标记，需人工确认 |
| 模型编排 | 计划必须过白名单/依赖/必需项/步数四道校验 | 模型给的顺序要能用，但不能成为正确性来源 | 编排器代码量增加，需维护依赖声明 |
| 可观测性 | plan / trace / context 直接随 API 返回 | 排障、评审、演示复用同一份数据 | 响应体更大，需要前端折叠 |
| 模型失败 | 连续 2 次失败熔断 60s，转默认编排 | 断网时不让每次请求都等超时 | 网络恢复后有最多 60s 降级窗口 |

## 二、踩坑记录

| # | 现象 | 根因 | 修法 | 通用教训 |
| --- | --- | --- | --- | --- |
| 1 | 双击 `start.bat` 报 `'…析助手' is not recognized`、`'rorlevel'` 被当命令执行 | cmd.exe 在 `chcp 65001` 后按字节偏移重读批处理文件，UTF-8 中文行被截断 | 批处理改纯 ASCII，中文提示交给 Python 打印 | 脚本文件的编码与解释器行为强耦合；跨平台脚本只放 ASCII |
| 2 | 第二个实例"成功"占用了同一端口 | Windows `SO_REUSEADDR` 允许重复绑定 | 绑定前主动 connect 探测占用 | 端口可用性不能只靠 bind 判断 |
| 3 | 模型 API 返回 usage 有值但正文为空 | `deepseek-flash` 是推理模型，reasoning tokens 先吃预算，`max_tokens` 给小了 | 放大 `max_tokens`，并识别 `reasoning_content` | 推理模型的"空回复"通常是预算问题，不是鉴权或参数问题 |
| 4 | 按需求描述配置的模型名 `deepseek-v4-flash` 不可用 | 端点真实 id 是 `deepseek-flash` / `deepseek-v4-pro` | 先列 `/models` 再配置 | 模型名必须实测确认，不能照抄需求描述 |
| 5 | 姓名抽取把"信息部总监张总"解析成"信息部" | 贪婪匹配 + 无姓名合法性校验 | 改为"称谓 + 最短可解释姓名"回溯匹配，并过滤角色词 | 中文人名/职务抽取必须做负向过滤，长匹配不代表正确 |
| 6 | 参会名单行（"客户参与人：陈经理、李主管、刘经理"）被当成影响人证据 | 名单行含"参与"等影响类关键词 | 识别名单标记词并跳过该句 | 结构化抬头行要显式排除，否则污染语义字段 |
| 7 | 章节标题"四、下一步行动"被当成一条下一步行动 | 标题含"下一步"关键词 | 加句子长度下限 + 必须含动作或未来标记 | 规则抽取要区分标题与正文，长度/句式是最便宜的判别信号 |
| 8 | 回顾式叙述"第一次沟通时说计划 6 月上线"被当成待办 | 有动作词 + "计划"被当作未来标记 | 引入回顾标记（第一次/上次/之前/已经）与强承诺标记的对抗判断 | "计划"不等于"待办"，时态判断是抽取准确率的分水岭 |
| 9 | 时间矛盾配错（"下周三"和"6 月"配成一对） | 冲突检测跨句配对，取了时间序列第一条 | 优先在同一句内识别改期词（推到/推迟），再退化为同里程碑比较 | 矛盾检测要限定"可比范围"，否则会把不相关条目配成矛盾 |
| 10 | "减少紧急调货"被识别为"时间紧迫"风险 | 单字关键词"急"命中"紧急" | 去掉单字关键词，只留多字表达并做否定过滤 | 中文单字关键词几乎必然误报，词表最小单位建议 ≥2 字 |
| 11 | 字段被判为"事实"，但证据句含"可能"，触发 R-01 告警 | 字段级证据混合了推断条目 | 条目级区分模糊性，字段值只取非模糊条目，模糊条目下沉为备注 | 状态判定要下沉到证据条目粒度 |
| 12 | 同一个人产生 5 条记录、描述关键词各不相同 | 只按出现次数收集，没有择优 | 按实体聚合 + 按关键词优先级打分保留一条 | 人物/实体类字段需要"聚合 + 打分"，不能简单累加 |
| 13 | `总预算 80 万` 与 `项目投入 45 万` 被判为矛盾 | 只比较金额数值 | 增加预算口径（总预算/项目投入/报价），跨口径抑制冲突 | 数值冲突检测必须考虑"口径"，否则误报率极高 |
| 14 | 环境里任何对外请求都以 WinError 10013 失败 | 沙箱限制，不是代码问题 | 先判定为环境性失败，再决定是否申请联网；同时给模型调用加熔断 | 区分"环境失败"与"代码失败"，避免误改代码 |
| 15 | 本会话没有可用浏览器，无法做可视化验收 | 运行环境缺浏览器实例 | 退化为接口冒烟 + 静态一致性检查 + JS 语法检查，并如实说明限制 | 验证手段要分级；不能因为"没法完美验证"就跳过验证 |
| 16 | 追问回答"预算 30 万"这类无上下文短语抽不出来 | 抽取器要求语境词（如"预算"） | 追问文本按字段加语境前缀后再抽取，仍抽不到则按字段兜底构造条目 | 多轮输入与首轮输入不是同一分布，需要对补全输入"补语境" |

## 三、下次开新项目先做的 10 件事

1. 先写清"判定权归属"，再选技术栈；
2. 把业务规则抽成外部配置文件（可读、可审、可 diff），代码里不写死；
3. 先定输出契约（字段 + 状态 + 证据 + 无法判断原因），再写抽取；
4. 定义降级链与熔断参数，把"最差情况"当一等公民；
5. 让每一步都产出可回放的 trace，评审和排障都靠它；
6. 准备覆盖不同失败形态的样例数据，并做成可一键加载；
7. 用生成器脚本生产测试数据（docx/pdf/txt），保证可重建；
8. 模型调用打桩测试四分支：正常 / 非法计划 / 失败 / 熔断；
9. 加反向断言（不得凭空补全），它比正向断言语义更强；
10. 交付前跑一遍"断网 + 无模型 + 无第三方库"的极限路径，确认还能用。
