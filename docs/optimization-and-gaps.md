# 这个 Agent 的不足与优化路线

先给结论：**当前版本能"现场演示、判定可审计、断网可跑"，但还不具备"上线生产"的成熟度**。
它的强项是判定确定性（规则引擎）与可解释性（证据 + 轨迹）；短板集中在**抽取能力上限、评估体系缺失、持久化与安全**三处。

## 一、能力边界（现在能做到 / 明确不做）

| 维度 | 现在能做到 | 现在明确不做 |
| --- | --- | --- |
| 输入 | 粘贴文本、txt/md/csv、docx、文本型 pdf；4 个内置样例 + 1 个 docx 测试文件 | 图片 OCR、语音转写、Excel 多行批量导入 |
| 抽取 | 需求、场景、预算（分口径）、决策人、影响人、时间计划、下一步、风险、未确认信息 | 语义级长句改写、跨文档实体消解、行业术语泛化 |
| 判定 | R-01~R-06 逐条校验、S0–S5 阶段判定、矛盾双记录、缺失标注 | 概率化置信度、自动规则学习、行业自适应 |
| 交互 | 结构化追问表单 + 重新分析、导出 JSON / CRM 摘要 | 自由对话问答、多用户协作、历史版本对比 |
| 运行 | 零依赖本地服务、可选模型规划与润色、失败熔断 | 账号体系、持久化、CRM 回写、并发压测 |

## 二、不足清单（按优先级）

### P0：影响"能不能被信任 / 能不能交付"

| # | 不足 | 影响 | 根因 | 优化方案 | 验收方式 |
| --- | --- | --- | --- | --- | --- |
| 1 | **没有评估集与指标** | 改词典/正则只能靠"看起来更准"，无法证明没有回归 | 测试是断言式的（29 个用例），不是统计式的 | 建 50–200 条标注样本的 golden set，输出字段级 P/R/F1、阶段准确率、矛盾召回率；CI 设阈值 | `eval/` 跑出指标报告，阈值不达标即失败 |
| 2 | **抽取召回受词典上限约束** | 客户说的新词、行业术语、口语化表达会漏 | 纯正则 + 词表，无语义层 | 引入向量/小模型做候选召回（判定仍归规则），词典缺口从失败样例自动挖掘 | golden set 上召回率提升 ≥10pt，且误报不增加 |
| 3 | **润色环节仍有改写风险** | 被刻意构造的文本可能诱导模型改写字段文案（判定面免疫，润色面不免疫） | 润色把字段值送进模型 | 润色结果做 diff 校验（数值/人名/时间不得变化）+ 一键关闭；或改为"只给建议、不直接落盘" | 注入用例集全部被拦截或标记待确认 |
| 4 | **无持久化与审计** | 关页即丢结果，无法复盘"谁在什么时候改了什么" | 服务端刻意无状态 | 加 SQLite/Postgres 落库 + 变更日志，保留 trace 与规则版本 | 可按 session 回放完整分析链路 |
| 5 | **无鉴权与限流** | 只能监听本机，一旦暴露到内网就是裸奔 | 演示形态的取舍 | 加 token/网关鉴权、请求体与频率限制、密钥走环境变量或密钥管理 | 未授权 401、超频 429 |

### P1：影响"好不好用 / 准不准"

| # | 不足 | 优化方案 |
| --- | --- | --- |
| 6 | 单商机假设，多商机只提示不拆 | 用"客户主体 + 项目名 + 预算值"聚类，先给拆分建议，用户确认后再拆成多张卡片 |
| 7 | 阶段判定是离散规则，没有置信度 | 输出"阶段 + 证据强度（满足条件数/证据条数/是否含模糊词）"，给人工一个可比较的分值 |
| 8 | "计划口径 vs 已进入口径"靠 guard 词维护 | 把 guard 词升级为时态/完成度小分类器（少量标注 + 规则混合），误判样例沉淀成回归用例 |
| 9 | 追问是模板化生成，不能反问澄清 | 让模型在"候选问题集"里做选择与排序（仍不产生业务结论），支持"为什么问这个"的解释 |
| 10 | 无 OCR / 语音转写 | 把 OCR/ASR 作为**上游工具**接入，统一产出文本后进入现有工具链（新增一个 `parse_*` 工具即可） |
| 11 | 规则与词典靠人工维护 | 加"未覆盖句子审计 → 新词候选 → 人工确认 → 回归"闭环，把 `audit_evidence_coverage` 的产物做成日报 |
| 12 | 无缓存与并发调优 | 对 `(文本哈希, 规则版本)` 做结果缓存；模型调用改为异步/后台任务，避免请求阻塞 2–5 秒 |
| 13 | 长文本一次性处理 | 按拜访分段切片抽取后再合并证据，避免长文被压缩影响召回 |

### P2：体验与工程化

| # | 不足 | 优化方案 |
| --- | --- | --- |
| 14 | 页面不能定位证据（只能看引文） | 在原文里高亮 evidence 的 span，点字段跳到对应句子 |
| 15 | 无字段 diff 视图 | 追问轮显示"上一轮 vs 本轮"逐字段对比（现在只高亮变化字段名） |
| 16 | 无日志与指标落盘 | 结构化日志 + 每次分析的耗时/模型调用/token 统计，落 JSONL 或接监控 |
| 17 | 规则之间缺乏一致性检查 | 加规则自检脚本：检测词表冲突（同一词同时出现在风险与正常语境）、阶段条件重叠 |
| 18 | 只支持中文 | 词典与正则按语言分包，抽取器按 locale 选择词表 |

## 三、建议的迭代批次

| 批次 | 目标 | 内容 | 大致成本 |
| --- | --- | --- | --- |
| 第 1 批 | 可信任 | golden set + 指标报告 + 润色 diff 校验 + 注入用例 | 1–2 天 |
| 第 2 批 | 更准更好用 | 向量召回补词典缺口 + 阶段证据强度 + 证据高亮 + 追问候选排序 | 3–5 天 |
| 第 3 批 | 可交付生产 | 持久化与审计 + 鉴权限流 + OCR/ASR 上游 + CRM 回写适配层 | 1–2 周 |

## 四、度量体系（把"感觉更准"变成可比较的数字）

- **字段级**：预算/决策人/时间计划/阶段的抽取准确率与召回率（对 golden set）；
- **状态正确率**：该判"推断"的有没有被写成"事实"（R-01/R-02 的核心指标，目标 100%，因为这是硬规则）；
- **缺失处理**：未确认字段是否出现"凭空补全"（目标 0）；
- **矛盾召回**：构造的矛盾用例是否都被 R-05 抓到、且不误报（口径差异如"总预算 vs 项目投入"已能做到不误报）；
- **追问有效性**：追问后字段状态升级比例、被标"客户未提及"的比例；
- **成本与延迟**：纯规则模式 <50ms；开启模型约 3–6s，模型调用 ≤2 次/请求。

## 五、明确不做（避免过度设计）

- 不让模型参与字段判定，哪怕短期看"更聪明"——一旦破例，题目要求的"判断依据来自给定规则"就不成立；
- 不为好看的 UI 引入前端框架与 CDN 依赖，牺牲"断网可跑"；
- 不做多租户与复杂权限，演示与单团队场景不值得这个复杂度。
