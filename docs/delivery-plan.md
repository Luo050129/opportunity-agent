# 重新设计这个项目的交付流程

适用对象：商机录入与分析助手 Agent（拜访记录 → CRM 十字段 + 规则校验 + 结构化追问）。

一句话原则：**判定权归属和输出契约必须在写第一行代码前锁死**，然后按
「契约 → 规则数据 → 确定性内核 → 编排 → 接口 → 界面 → 加固 → 评估交付」推进，
每个里程碑都要能端到端演示。

当前基线（可作为对照）：`rules/` 已外置 R-01~R-06 与 S0–S5；`agent/tools.py` 提供 10 个带
`requires/produces` 契约的确定性工具；编排器具备白名单、依赖补齐、必需项兜底、步数上限；
29 个用例全绿，0.66s 跑完。短板集中在三处：缺 golden set 与指标、`agent/extract.py` 单文件 605 行、
润色环节仍有改写风险。

## 一、需求分析：把题目翻译成可验收基线

输入是三类材料：题目原文的硬规则、使用者的真实任务、环境约束（现场演示、断网、可能没装包）。

### 1.1 四个动作

1. **需求分层**：业务目标 → 用户任务 → 功能需求 → 非功能需求 → 边界与降级需求。
   后两类最容易被忽略，也最影响评分。
2. **区分硬约束与待决问题**。硬约束不可谈判：判定必须来自题目给定规则、每条结论要有原话证据、
   信息不足不得补全。待决问题（多商机是否自动拆分、要不要 OCR、要不要持久化）当场给默认值
   并记入「明确不做」，不留给开发阶段临时决定。
3. **先定判定权归属表，再谈选型**。谁产出字段值、状态、阶段、合规结论（确定性规则），
   谁只做理解与调度（模型）。这张表决定后面所有模块边界。
   落地形式：**规则引擎 = 工具集，模型 = 规划器 + 文案润色器**。
4. **验收标准随需求一起产出**。需求条目不写「支持预算抽取」，而写
   「预算按总预算/项目投入/报价分口径；命中模糊措辞不得写成事实；未确认时 `value` 为 `null` 并注明来源」。

### 1.2 需求阶段出口物（四份，缺一不算完成）

| 出口物 | 内容 |
| --- | --- |
| 需求基线 | 业务目标、用户任务、功能/非功能需求、明确不做清单 |
| 输出契约 | 字段结构 JSON Schema（`value/status/evidence/items/notes/rule_refs`） |
| 规则映射表 | R-01~R-06 + S0–S5 达成条件 + 词典，与需求条目一一对应 |
| 验收标准矩阵 | 需求 ↔ 规则 ↔ 测试用例 一一对应，可执行 |

### 1.3 需求到验收的映射（节选）

| 需求条目 | 规则来源 | 验收标准 | 责任模块 |
| --- | --- | --- | --- |
| 字段三态 + 原话证据 | R-01/R-02/R-04 | 模糊句不得判 confirmed，目标 100% | 抽取 + 字段组装 |
| 缺失不补全 | R-03 | 未确认字段 `value` 必须为 `null`，补全数 0 | 字段组装 |
| 矛盾双保留 | R-05 | 矛盾用例召回，且跨口径不误报 | 矛盾检测 |
| 阶段判定 + 缺证据说明 | S0–S5 达成条件 | 无签约原话不得判 S5，被拦阶段须说明缺什么 | 阶段判定 |
| 下一步含负责人/时间 | R-06 | 缺失须标「待确认」并生成追问 | 字段组装 + 追问 |

## 二、任务拆分：横向分层 × 纵向里程碑

横向分层决定接口和文件归属，纵向切片保证每个里程碑都能端到端演示。

横向七层：契约层 / 规则数据层 / 抽取内核 / 判定内核 / 编排层 / 服务与接口层 / 展示层。

| 里程碑 | 交付物 | 出口标准 | 依赖 |
| --- | --- | --- | --- |
| M0 契约与骨架 | 需求基线、Schema、空壳链路 | `/api/analyze` 能返回合法契约（全字段 unconfirmed） | — |
| M1 规则数据层 | `rules/*.json`、加载器、规则版本 | 规则零硬编码，`rule_id` 可回溯原文 | M0 |
| M2 抽取内核 | 分句 + 条目级抽取，条目带 `vague/source/turn` | golden set 召回阈值达标 + 反向断言通过 | M1 |
| M3 判定内核 | 字段组装、三态、阶段、R-01~R-06、矛盾 | 每条硬规则一正一反全绿 | M2 |
| M4 编排层 | 工具契约、默认编排、模型规划、四道校验 | 打桩四分支通过；开关模型判定一致 | M2 |
| M5 交互层 | 追问闭环、文件解析、Web/API | 追问后字段升级与阶段推进可验证 | M3、M4 |
| M6 加固 | 降级链、熔断、双轨上下文、plan/trace/context | 极限路径（断网+无模型+无三方库）可用 | M5 |
| M7 评估与交付 | 指标报告、交付四件套、校验清单 | 指标达标 + 环境矩阵全通过 | M6 |

并行策略：M0 冻结契约后可以三线并行——抽取内核、编排骨架、前端（用 mock 契约先行）。
单人做则严格串行，谁都不能跳过 M0。

## 三、技术选型：用约束反推，并写明反转条件

选型判据排序：演示环境确定性 > 结论可审计 > 开发速度 > 性能并发。

| 维度 | 候选 | 选择 | 判据 | 反转条件 |
| --- | --- | --- | --- | --- |
| 服务 | 标准库 http.server / FastAPI | 标准库 | 断网、免安装即可跑 | 要内网多用户并发 → FastAPI |
| 前端 | 原生 / React | 原生 | 无 CDN、离线可用 | 要复杂交互与协作 → 构建型前端 |
| 判定主体 | LLM-first / 规则+LLM | 规则引擎 | 结论必须可回溯到规则原文 | 题目放开自由判断才考虑 |
| 规则存储 | 代码常量 / JSON 外置 | JSON | 可读、可审、可 diff | 规则量大且需版本化 → 规则库+迁移 |
| 会话 | 服务端 session / 前端回传 | 无状态 | 重启不丢、多窗口并行 | 要审计回放 → 落库 |
| 模型客户端 | 官方 SDK / urllib | urllib | 保持零依赖，模型本身可选 | 要用流式与重试框架 → SDK |
| 测试 | pytest / unittest | unittest | 零依赖 | 要参数化与 fixture → pytest |
| 持久化 | 无 / SQLite | 演示不落库 | 演示形态取舍 | 生产化批次 → SQLite/Postgres |

## 四、模块开发：契约先行，每模块先冻结三样

开工前每个模块必须冻结：输入输出结构、依赖声明、**不变量**。
不变量最关键，例如：

- 抽取器不得直接写 `status`；
- 工具必须确定性幂等，同输入同输出；
- 模型不得产出字段值、证据、阶段、合规结论。

开发顺序：规则数据 → 抽取 → 判定 → 编排 → 接口 → 界面。测试与模块同步写，不留到最后统一补。

对现状最大的一处重构建议：`agent/extract.py` 605 行按字段拆成 extractor 注册表，
每个 extractor 声明「负责字段、依赖的词典键、产出条目、正反例」。
这样新增字段等于新增插件，词典缺口也能按字段定位。
另外把状态判定下沉到条目粒度——字段值只取非模糊条目，模糊条目下沉为备注。

## 五、模块测试与验收：分层 + 量化出口

| 层次 | 做法 | 出口标准 |
| --- | --- | --- |
| 契约测试 | 校验字段结构、三态取值、证据必填 | 契约违规 0 |
| 单元正反例 | 每条硬规则 ≥1 正 1 反 | 全绿 |
| 反向断言 | 断言输出不得出现凭空金额/姓名/阶段 | 全绿 |
| 样例端到端 | 完整/缺失/矛盾/模糊四类输入 | 字段与阶段断言全绿 |
| 打桩测试 | 合法计划/非法计划/调用失败/熔断 | 四分支全绿，不依赖网络 |
| 解析降级 | 编码识别、docx、文本 PDF、扫描 PDF、图片 | 失败路径有可操作提示 |
| 接口冒烟 | `/api/*` 含 422 路径 | 全绿 |
| 统计评估 | golden set 字段级 P/R/F1、矛盾召回 | 达阈值，CI 不达标即失败 |

两类标准要分开：**R-01/R-02 这类硬规则用断言锁死，目标 100%**，因为它们不是概率问题；
只有抽取召回才用统计阈值。

模块退出标准统一为：基线用例全绿 + 量化指标达标 + 无 P0 缺陷；契约一旦变更就触发全量回归。

## 六、整体联调：契约冻结 + 一致性验证

四条联调主线：

1. **契约联调**：前端只依赖 `/api/analyze` 契约，用固定 JSON 做快照，字段结构变动立即报警。
2. **降级矩阵联调**：正常 / 模型不可用 / 非法计划 / 工具异常 / 解析失败 / 空输入 /
   超长文本 / 多轮追问 / 端口占用，每条都要有「用户看得懂的下一步」。
3. **一致性验证**（本项目最有价值的联调断言）：**开模型与关模型，字段值、状态、证据、阶段、
   合规结论必须逐字段一致**，只允许 `plan.source` 与润色文案不同。它一次性证明模型没有偷走判定权。
4. **性能与成本预算**：纯规则 <50ms，开模型 3–6s，模型调用 ≤2 次/请求，2 次失败熔断 60s。

联调出口：场景矩阵全通过，`trace` 每步可读，且任意降级路径下的输出仍满足契约。

## 七、交付校验：环境矩阵 + 四件套 + 指标报告

交付物：一键入口（双击启动、端口顺延、失败不闪退）、使用说明、规则说明、输出格式说明、
自测样例、接口清单、指标报告、遗留问题与边界说明。

环境矩阵逐项实跑：Windows 双击 / 断网 / 无第三方包 / 无模型 / 端口被占用 /
无浏览器（降级为接口冒烟 + 静态一致性 + JS 语法检查）。
最后跑一遍极限路径——断网 + 无模型 + 无三方库，确认样例仍可用。

交付时主动写明边界：OCR、多商机自动拆分、持久化、鉴权限流属于下一批次；
把「无法判断」做成一等功能展示。

## 八、如果重来，我会改的六处

1. golden set 与指标前置到 M2 之前，不等交付才补——这是当前唯一的 P0。
2. 输出契约在 M0 冻结，避免引擎先成型、契约随后固化。
3. `agent/extract.py` 拆成 extractor 插件，状态在条目级产出。
4. 证据从 `quote` 文本升级为字符区间（span），支持前端高亮定位。
5. 润色加 diff 校验（数值/人名/时间不得变）与注入用例集——判定面已免疫，润色面是当前唯一薄弱点。
6. 多商机拆分、持久化审计、鉴权限流明确划入生产化批次，不进演示批次。
