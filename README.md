# 商机录入与分析助手 Agent

把销售拜访记录变成可复核的 CRM 商机：**CRM 十字段结构化 + 规则校验报告 + 结构化追问**。
判定主体是题目给定规则的确定性规则引擎（R-01 ~ R-06、S0–S5 达成条件），不依赖大模型常识自由判断；
每条结论都带状态（事实／推断／未确认）与原话证据，信息不足时明确输出「无法判断，建议人工复核」。

## 1. 访问入口

零依赖、断网可跑：只用 Python 标准库，不需要安装任何第三方包。

```bash
python app.py            # 打开 http://127.0.0.1:8000/
python app.py --port 8801 --open   # 换端口并自动打开浏览器
```

Windows 下双击 `start.bat` 即可（默认端口 8000 并自动打开浏览器）。脚本行为：

- 自动识别 `python` 或 `py -3`，并校验版本 ≥ 3.10，缺失时窗口不会一闪而过，而是给出安装提示并等待按键；
- 端口被占用时自动往后找可用端口（8000 → 8001 → …），控制台会打印实际访问地址；
- 启动失败保留窗口并打印退出码与排错命令；
- 脚本内容保持**纯 ASCII**：cmd.exe 在 `chcp` 切换代码页后会按字节偏移重新解析 .bat，含中文的行会被截断成乱码命令，这是之前双击报 `'xxx' is not recognized` 的原因。

服务只监听本机回环地址，页面顶部会显示「判定引擎：规则引擎」「大模型：未启用」（如果未配置LLM）。

## 2. 使用说明：支持什么输入

| 输入方式 | 支持情况 |
| --- | --- |
| 直接粘贴文本 | 支持，推荐方式（中文拜访纪要、通话记录、微信聊天文字等） |
| 上传 `.txt` / `.md` / `.csv` | 支持，自动识别 UTF-8 / GB18030 编码 |
| 上传 `.docx` | 支持（标准库解压 + 解析 `word/document.xml`） |
| 上传文本型 `.pdf` | 支持轻量解析；扫描件、加密 PDF、自定义字体编码会**明确提示无法解析**，并建议改为粘贴文本 |
| 图片 / 截图 | 不支持 OCR，会提示「请把截图文字粘贴为文本」 |
| 一份记录含多个商机 | 默认按单商机分析，检测到多个客户主体时给出「建议拆分」提示，不自动拆分 |

页面内置 4 个一键样例提供测试，点一下即可载入并分析。

## 3. 规则使用说明

全部规则、阶段定义与词典都放在 `rules/` 目录，代码里不写死业务规则，页面「规则依据」面板可只读展开查看原文：

| 文件 | 内容 |
| --- | --- |
| `rules/check_rules.json` | R-01 事实边界、R-02 推断处理、R-03 缺失信息、R-04 证据要求、R-05 矛盾处理、R-06 下一步行动，以及字段风险等级、必须有证据的字段 |
| `rules/stage_definitions.json` | S0 线索、S1 需求初探、S2 方案验证、S3 商务评估、S4 决策审批、S5 赢单/签约的达成条件、关键词、否定/计划性口径拦截词 |
| `rules/lexicon.json` | 模糊措辞表、金额与时间正则、预算口径词、决策/影响称谓词、场景词典、风险与竞争词、需求失效词、下一步动作词等 |

规则怎么落到判定上：

1. **抽取**：预算按金额正则 + 预算语境词，且区分「总预算／项目投入／报价」口径；决策人按「称谓 + 最短可解释姓名」匹配，并排除「不是张总」这类否定表述；时间计划要求同一句出现里程碑语境，纯我方动作时间不会写成客户计划。
2. **状态判定**：命中「可能、应该、感觉、挺感兴趣、大概、左右、看情况」等模糊措辞的句子，一律降级为「推断／未确认」；同一字段既有事实又有推断时，字段值只写事实，推断内容进入备注与未确认清单。
3. **阶段判定**：自 S5 向 S0 扫描，取「达成条件满足 + 有原话证据」的最高阶段；提到但处于计划/未完成口径（如「合同正在走流程」「计划 5 月完成立项审批」）会被拦下，并写入「未满足 / 被拦下的更高阶段」说明缺什么证据。
4. **矛盾处理**：预算金额、时间计划、决策人、需求失效四类冲突同时保留双方原话，标为待确认，并触发 R-05 高风险项；「总预算」与「项目投入」这种口径差异不会误判成矛盾。
5. **失败降级**：文件解析失败、输入过短、规则未覆盖时，输出「无法判断原因 + 建议人工复核」，而不是猜测结论；阶段无法判定时还会列出「未被现有规则覆盖的内容」，说明哪些表述引擎没有做判断。

## 4. 输出格式说明

**CRM 十字段**：需求、核心场景、预算、决策人、影响人、时间计划、阶段、风险、下一步、未确认信息。
每个字段结构为：

```json
{
  "field": "预算",
  "value": "总预算80 万；项目投入45 万",
  "status": "confirmed",
  "evidence": [{ "quote": "陈经理说今年 IT 预算已经批下来 80 万", "matched": "80 万", "source": "input", "turn": 0 }],
  "items": [{ "display": "项目投入45 万", "scope": "项目", "amount": 450000, "currency": "CNY" }],
  "notes": [],
  "rule_refs": ["R-01", "R-03", "R-04", "R-05"]
}
```

- `status`：`confirmed` 事实 / `inferred` 推断 / `unconfirmed` 未确认（未确认时 `value` 为 `null`，不做补全）。
- `下一步` 每条为「动作 + 建议负责人 + 时间」，未约定时间写「待确认」。
- `阶段` 含 `code / name / status / condition / satisfied_conditions / blocked_by / conflicts / cannot_judge_reason`。

**规则校验报告**：`overall`（是否合规、风险等级、问题数、结论摘要）+ 问题清单，每条包含
`severity`、`issue_type`、`message`（具体问题）、`rule_id`/`rule_text`（对应规则原文）、`suggestion`（整改建议）、
`evidence`（原话证据）、`cannot_judge_reason`（无法判断原因）。

**追问闭环**：未确认字段、矛盾项、缺少负责人/时间的下一步、阶段无法判定，都会生成结构化问题；
在页面上回答后系统会作为新证据重跑全部规则，刷新字段与阶段，并高亮「本轮发生变化的字段」。
回答「未确认 / 客户未提及」会保留未确认标注并停止重复追问，而不是补全内容。

**导出**：可下载完整 JSON，或一键复制 CRM 字段摘要文本。

## 5. 自测样例（真实运行结果）

### 样例 1：规范完整记录（`samples/01_规范完整记录.txt`）

- 阶段：**S4 决策审批**（confirmed）——「客户已在 3 月初提交内部立项申请，上周已上评审会，目前正在走供应商决策流程」；S5 被拦下并说明「未出现达成条件所需证据（关注词：签合同、签约、已签 等）」。
- 预算：**总预算80 万；项目投入45 万**（事实，附两条原话，且识别为不同口径不判矛盾）。
- 决策人：**张总（签字）**；影响人：**陈经理（推动、评估）；刘经理（对接、使用）**。
- 时间计划：**下周三；4 月底（技术验证）；5 月底（立项）；6 月（上线）**。
- 风险：竞争信号「另一家供应商」「也在看」+ 客户顾虑「担心项目实施周期太长」。
- 下一步：3 条，均写明动作、负责人与时间（如「我这边周五之前把技术交流的详细方案和报价单发给陈经理（负责人：我方；时间：周五）」）。
- 校验结论：**合规，风险等级 无，0 项问题**，关键字段均有原话依据。

### 样例 2：关键信息缺失（`samples/02_关键信息缺失.txt`）

- 阶段：**S1 需求初探**；S2/S3/S4/S5 全部被拦下，例如「提到『预算』，但关键词处于否定/未确认表述中（如"没提到""还没定"），不构成达成证据」。
- 预算、决策人、影响人、时间计划：全部 `unconfirmed`、`value` 为 `null`，未确认信息里写明「原始记录中未提供，按 R-03 标注未确认、不做补全」。
- 校验结论：**需要整改，风险等级 高**，命中 R-03 高风险项（预算、决策人缺失）与 R-06（下一步未约定负责人/时间）。
- 追问：自动生成「客户是否透露预算范围」「最终决策人是谁」等待确认问题。
- 追问闭环实测：补充「预算 30 万，已经内部批下来了」「张总，信息部总监，最终签字」「计划 5 月底完成采购审批」后，预算/决策人/时间计划转为**事实**，阶段由 **S1 升级为 S3**，S3 从拦截列表消失，证据来源标记为「补充确认·第 N 轮」。

### 样例 3：前后矛盾（`samples/03_前后矛盾.txt`）

- 阶段：**S3 商务评估**（inferred），并附「阶段涉及的字段存在矛盾证据，已同时保留，需人工确认哪一版为准」。
- 矛盾同时保留：预算「项目投入30 万 / 预算50 万」、时间「6 月（上线） / 9 月（上线）」、决策人「王总 / 陈副总」。
- 校验结论：**需要整改，风险等级 高**，3 条 R-05 高风险项，每条都带双方原话与「无法判断原因：客户前后表达矛盾，需人工确认哪一版为准」。
- 追问：直接针对三处矛盾各生成一个问题，询问「哪一版是客户最新确认的口径」。

### 样例 4：模糊措辞（`samples/04_模糊措辞.txt`）

- 需求：「上一套招生管理系统」判为**推断**（原话含「可能」「挺感兴趣」）；核心场景「招生管理系统」同为推断。
- 阶段：**S0 线索**（inferred），S1 被拦下并写明「对应字段未达到"明确"要求：需求（当前状态：推断）」。
- 预算、决策人、时间计划：`unconfirmed`，未确认信息注明「仅有推断性表达，未获得客户明确确认」「提到预算但为未确认表述（没提、不确定、没提到）」。
- 校验结论：命中 **R-02**「检测到模糊表述，已按规则降级为推断/未确认，未写成确定结论」。

| 接口 | 说明 |

| `GET /api/samples` | 4 个内置样例 |

`POST /api/analyze` 的返回还额外包含三个可审计部分：`plan`（本次工具计划来自模型规划还是规则引擎默认编排、模型给的编排理由、被拒绝的非法工具）、
`trace`（逐步工具调用轨迹：工具名、理由、状态、产物、耗时）、`context`（上下文预算统计）。页面底部「执行轨迹」面板与之一一对应。

## 7. 大模型接入（可选，默认按配置开关）

判定永远是规则引擎做的；模型只负责**规划工具调用顺序**与**润色已确认字段的表述**。开关优先级：

| 方式 | 说明 |
| --- | --- |
| `--enable-llm` | 强制开启（需有可用 key） |
| `--no-llm` | 强制关闭，纯规则引擎，输出完全确定 |
| 二者都不给 | 读 `llm.local.json` 的 `enabled`；没有该文件即默认关闭 |
| `--llm-model` / `--llm-base-url` | 临时覆盖模型名与服务地址 |
| 环境变量 | `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`（优先级高于配置文件） |

`llm.local.json`（**含密钥，已加入 .gitignore，不要随项目分发**）：

```json
{
  "enabled": true,
  "base_url": "https://api.deepseek.com",
  "model": "deepseek-flash",
  "api_key": "sk-...",
  "timeout_seconds": 30
}
```

实测记录：该端点的可用模型为 `deepseek-flash` 与 `deepseek-v4-pro`，**没有** `deepseek-v4-flash` 这个 id；
`deepseek-flash` 是推理模型，会额外返回 `reasoning_content`，因此规划调用需要留足 `max_tokens`。
启动时控制台会打印实际使用的模型与地址；模型不可用时自动回退到规则引擎默认编排，页面仍可正常使用。

更多细节见 [docs/agent-architecture.md](docs/agent-architecture.md)：自主规划、工具调用、上下文管理、流程编排四个维度的实现说明。

## 10. 边界与默认值

- 大模型默认按 `llm.local.json` 决定；`--no-llm` 可随时退回纯规则引擎，此时输出完全确定、零外部调用。
- 模型无写权限：不能产出字段值、状态、证据、阶段或合规结论；唯一的写权限是润色已确认字段的文案。
- 输入以中文拜访记录为主；不做图片 OCR；不写回真实 CRM，只导出 JSON / 摘要文本。
- 单商机为默认处理单元；无账号体系、无数据库、无持久化，服务仅监听本机。
- 规则未覆盖的业务判断不会自行发挥，一律输出「无法判断，建议人工复核」。
